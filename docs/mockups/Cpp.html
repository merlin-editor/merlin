1 · Getting around C++ code
Right-click on a name gives every way to follow it, with its key. The entries come from what the file's language server can do, so the menu is the same for Rust, Go or Python, less what their server lacks. Go to Implementations gets Ctrl+F12 here, as merlin's own binding, which plugins can't take.

Call and Type Hierarchy (Shift+Alt+H; 380 and 114 votes) open in a view of their own. Callers go up, Callees down, each level opened as asked, as the LSP's callHierarchy calls it. A click opens the call, a row's count says how many calls it makes there. Types shows a class's bases or the classes derived from it.

The name's other uses light up when the cursor rests on one, from the server's documentHighlight: where it's written in amber with a line under it, where it's read in blue, and marks in the scrollbar. Without a server, the same word in the file, faintly.

2 · The debugger, closer to the machine

For every language whose debugger has them (gdb and lldb-dap for C, C++, Rust, Zig, Go), as the debug protocol's own requests: disassemble, readMemory, instruction stepping and stepInTargets. The most voted C/C++ requests after renaming (436, 367 and 345 votes).

Disassembly (Debug › Open Disassembly, or right-click a frame) opens beside the source and follows it: the paused instruction marked as the paused line is, the source line each run of instructions comes from above it in grey, calls named. Breakpoints go on an instruction too. Step by instruction switches F10 and F11 to one instruction at a time, and the toolbar shows ⤼ i while it's on.

Memory is a bottom panel tab: an address, or any expression (&total, rects.data()), then rows of 16 bytes with their text. The bytes of the expression are tinted, ones that changed since the last stop are amber. Right-click a variable for "Show in Memory"; a variable's row shows its address faintly.

Skip library code ("Just My Code"), on by default: Step Into steps over code from the standard library and the system's headers (outside the workspace), as gdb's skip and lldb's step-avoid settings do. The call stack folds library frames into one line, as it does today.

3 · Setting a project up, and every file's errors

No compile commands: today clangd guesses each file's flags, and a project that needs any include folder shows red everywhere with no word why. When clangd says it's guessing (its fileStatus, or no compile_commands.json found), a bar over the file says so, once per project, with what would fix it here: Configure with CMake when the CMake plugin finds a project that isn't configured (it shares the build's file, as today); Configure Meson and the like from other build plugins; else Set Include Folders…, which opens the C/C++ plugin's settings. ✕ hides it for the project. The language's status item turns amber, "C++ · guessing flags", and its card says the same with the same buttons, so the bar can go and the help stays.

Errors for the whole project (29 votes for clangd): clangd reports only open files. Whole Project in Problems checks every file compile_commands.json lists, a few at a time in the background, with clangd's own --check or the compiler's -fsyntax-only, clang-tidy's findings too when the project has a .clang-tidy. A spinner says how far it's got, Stop stops it, and it runs again on Save All or by hand, not on every keystroke. Open files keep their live problems from clangd, marked "open". The status bar counts follow the scope picked.
