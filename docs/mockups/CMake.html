1 · The build in the status bar
In a project with a CMakeLists.txt, the status bar shows the preset (or the build folder without presets) and the target, as CMake Tools does, whatever file is open.

A click on either opens a picker over it. Picking a preset configures it if it hasn't been. The targets come from CMake's file API, programs first. One target is both what ⚒ Build (F7) builds and what ▶ Run (Ctrl+F5) and 🐞 Debug (F5) start, so there's one choice to make, not two (CMake Tools #1941).

Both cards are open here to show them; only one opens at a time. The chips are a plugin's status items, so any build plugin (Meson, Cargo) can use them.

2 · The CMake view A view in the rail, from the plugin's [[views]], for what the status bar can't hold.

The build: its preset, generator, folder and when it was last configured, with Configure. ↻ reloads; ⋯ has Configure from Scratch, Clean, Install and Open CMakeCache.txt.

Targets by their FOLDER property, else their directory (CMake Tools #491). Each has Build, and programs Run and Debug, on hover; ◎ marks the target the status bar has. Opening a target lists its sources; a click opens one.

Tests is CTest's, as the Tests view has them, folded to its count.

Cache: every variable CMake keeps, with a filter, as CLion has them. Booleans are switches, a variable with its STRINGS property is a choice, the rest boxes. A change waits, marked, until Configure passes it as -D; Undo drops it. Advanced variables hide behind ⋯ › Show Advanced.

What needs no mock-up and is built (2026-11-17): Configure, Build and Test tasks from presets; a Build task per target and Run per program; programs in Run and Debug (F5) with the C/C++ plugin's debugger; CTest's tests in the Tests view at their add_test lines, run in parallel and debuggable; configure on save; settings for the build folder, type, generator and cache variables; neocmakelsp for completion and hover; and the build shared with clangd.

Today's list for comparison: one case per name (CMake's commands are case-blind, so ADD_CUSTOM_COMMAND and add_custom_command become one row, in the file's case), and the kind as a mark, not the word "Function" on the right.
ADD_CUSTOM_COMMANDFunction
add_custom_commandFunction
The name is in the colour of its kind, as the code shows it: functions in the function colour, types in the type colour, constants and CMake variables in the constant colour, fields and variables in the text colour. The letters you typed are underlined in the accent colour and slightly bolder, wherever they matched (fuzzy, as emplace_back).

The kind mark on the left (ƒ function, T type, ◆ field, V variable or constant, ! macro, K keyword, M module) is tinted to match, so the list scans by colour and shape, as in VS Code and JetBrains. The detail on the right, a signature or type, is coloured with the language's own colours at half strength, as Zed does, so the name still leads; the chosen row brings it to full strength.

The chosen row also opens its documentation under the list: the full signature, coloured, and the first line of its docs, with Ctrl+Space to show more. Rows other than the chosen one stay muted, so the list never becomes a wall of colour.

For plugin authors (plugin API 0.16, not released yet): a completion gains kind (the LSP's CompletionItemKind, which the LSP SDK passes on) and documentation. The editor colours the name by kind and marks the matched letters itself; the detail and the signature are coloured by the plugin's colour-text, which language plugins already have for diffs and Markdown. A plugin without it gets plain, dimmed details.
